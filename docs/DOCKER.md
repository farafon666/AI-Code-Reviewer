# Запуск AI Code Reviewer в Docker

В репозитории уже есть Dockerfile для каждого приложения и готовый
`docker-compose.yml`. Основная команда запуска из корня проекта:

```sh
docker compose up -d --build
```

После сборки образов и подготовки модели интерфейс будет доступен по адресу
[http://localhost:3000](http://localhost:3000). На первом запуске нужно дождаться
скачивания модели. Ниже описаны подготовка, проверка результата и обслуживание.

## 1. Как устроен проект

| Каталог или файл        | Назначение                                                                                                        |
| ----------------------- | ----------------------------------------------------------------------------------------------------------------- |
| `apps/host`             | Основное приложение на React 18 и TypeScript; загружает компонент ревью из remote через Webpack Module Federation |
| `apps/remote`           | Самостоятельное React-приложение и микрофронтенд с формой отправки кода                                           |
| `backend`               | API на Express; запускает ESLint в worker thread, затем запрашивает ревью у Ollama через LangChain                |
| `docker-compose.yml`    | Объединяет приложения, сервер модели и одноразовую подготовку модели                                              |
| `apps/*/nginx.conf`     | Раздача собранных frontend и проксирование запросов                                                               |
| `backend/src/config.js` | Значения по умолчанию и проверка настроек backend                                                                 |

Базы данных, Redis, регистрации пользователей и хранения истории ревью в проекте
нет. Исходный код из формы передаётся на статический анализ и в модель;
backend не запускает его как программу. Текущая конфигурация ESLint разбирает
JavaScript/JSX; TypeScript parser и анализаторы других языков не подключены.

Compose создаёт пять сервисов:

| Сервис        | Что выполняется                               | Адрес внутри сети Compose   | Доступ с компьютера          |
| ------------- | --------------------------------------------- | --------------------------- | ---------------------------- |
| `host`        | Nginx с production-сборкой основного frontend | `http://host:80`            | `http://localhost:3000`      |
| `remote`      | Nginx со сборкой микрофронтенда               | `http://remote:80`          | `http://localhost:3001`      |
| `backend`     | Node.js 24, Express и ESLint                  | `http://backend:5000`       | Через `/api/` обоих frontend |
| `ollama`      | Сервер локальной LLM                          | `http://ollama:11434`       | Порт не опубликован          |
| `ollama-init` | Проверка наличия и загрузка модели            | Обращается к `ollama:11434` | Завершается после подготовки |

Путь обычного запроса:

```text
Браузер → localhost:3000/api/review → Nginx host → backend:5000/review
                                                    ├─ ESLint worker
                                                    └─ ollama:11434
```

Host получает микрофронтенд через `/remote/remoteEntry.js` и `/remote/<chunk>.js`.
Nginx перенаправляет эти пути на `remote:80`. При открытии remote на порту 3001
запросы `/api/` идут через его собственный Nginx в тот же backend.

JS-файлы сборки получают имена с хешем содержимого. HTML и `remoteEntry.js`
отдаются с `Cache-Control: no-cache`, поэтому браузер проверяет их актуальность
при новой загрузке страницы; этот заголовок remote сохраняется и через прокси host.
Открытую до обновления вкладку нужно перезагрузить. После перехода со старой
сборки без этих правил кеширования один раз используйте `Ctrl+F5` на обоих адресах.

Контейнеры находят друг друга по именам сервисов. `localhost` внутри контейнера
означает сам этот контейнер, поэтому заменять `http://ollama:11434` на
`http://localhost:11434` в Compose нельзя.

## 2. Что установить и подготовить

### Windows

1. Установите [Docker Desktop для Windows](https://docs.docker.com/desktop/setup/install/windows-install/).
2. Для описанного ниже варианта включите WSL 2 backend и используйте Linux
   containers: образы проекта основаны на Linux.
3. Запустите Docker Desktop и дождитесь готовности движка.
4. Откройте PowerShell и перейдите в каталог проекта:

   ```powershell
   Set-Location 'D:\JSProjects\AI-Code-Reviewer'
   ```

Для проверки WSL при проблемах с Docker Desktop:

```powershell
wsl --status
wsl --version
```

### Linux

На Linux подойдут Docker Engine и Compose plugin.
Инструкции установки доступны в [документации Docker Compose](https://docs.docker.com/compose/install/).
В терминале перейдите в корень своей копии репозитория.

### Проверка Docker

Эти команды одинаковы для PowerShell и Bash:

```sh
docker version
docker compose version
docker info --format '{{.OSType}}'
```

У `docker version` должны отображаться разделы Client и Server;
последняя команда должна вывести `linux`. Если клиент есть, а Server недоступен,
сначала устраните проблему доступа к Docker Engine.

Используйте актуальный Compose с командой `docker compose`.
Отдельно ставить Node.js, npm, Nginx или Ollama на компьютер для этого сценария
не требуется. API-ключи внешних LLM-сервисов также не нужны.

### Память, диск и сеть

На первом запуске нужен интернет для образов из Docker Hub, пакетов npm и модели
из реестра Ollama. Сеть должна быть доступна как Docker Engine, так и контейнерам.
После подготовки обычные ревью используют локальный контейнер Ollama;
при повторной сборке или смене модели доступ к реестрам может потребоваться снова.

Модель по умолчанию — `qwen2.5-coder:7b`. В каталоге Ollama её размер указан как
примерно 4,7 ГБ; вариант `qwen2.5-coder:1.5b` занимает примерно 986 МБ.
Это размеры файлов модели, а не требования к оперативной памяти:
[7b](https://ollama.com/library/qwen2.5-coder:7b),
[1.5b](https://ollama.com/library/qwen2.5-coder:1.5b).

Оставьте дополнительное место под образы, npm-зависимости и кеш сборки.
Фактическое потребление RAM/VRAM зависит от модели и размера контекста:
увеличение контекста повышает требования к памяти, как описано в
[документации Ollama](https://docs.ollama.com/context-length).
У проекта по умолчанию задан контекст 32768 токенов. Для первого пробного запуска
на машине с ограниченной памятью можно выбрать профиль из следующего раздела;
фиксированного гарантированного минимума RAM для всего приложения в проекте нет.
Учитывайте лимит памяти, доступной Docker/WSL, а не только RAM компьютера.

Основной Compose запрашивает NVIDIA GPU для Ollama.
Первый ответ включает загрузку модели в память и может быть заметно медленнее
следующих.

## 3. Подготовка репозитория к сборке

Все дальнейшие команды запускайте из каталога с `docker-compose.yml`.
Корневой `package.json` содержит инструменты автоматических проверок. Для сборки
и запуска через Docker устанавливать npm-зависимости на компьютере не требуется.
Для локального `npm run check` установите их по инструкции в разделе
[«Проверка» README](../README.md#проверка).

У каждого приложения уже есть собственный `.dockerignore`, поскольку Compose
использует отдельный build context для каждого из них. Backend исключает
`node_modules`, `.env` и `test`. Оба frontend исключают `node_modules`, `dist`,
`.env`, `.env.*` и `npm-debug.log*`. Локальные зависимости и результаты сборки
frontend не попадают в контекст и не перезаписывают файлы контейнера при `COPY . .`.

Перед установкой зависимостей frontend Dockerfile явно копируют `package.json`
и `package-lock.json`. Команда `npm ci` устанавливает зависимости по lock-файлу,
не изменяет его и завершает сборку с ошибкой при рассогласовании с `package.json`.
DevDependencies сохраняются на этапе сборки: они нужны Webpack и TypeScript.
Там же устанавливаются тестовые инструменты remote, которым нужен современный Node.js.
Оба frontend собираются на Node.js 24, как backend и CI; в итоговые Nginx-образы
копируются только `dist` и конфигурация сервера.

## 4. Настройка модели и переменных окружения

### Запуск с настройками проекта

Файл `.env` необязателен: Compose уже содержит значения по умолчанию, включая
`OLLAMA_MODEL=qwen2.5-coder:7b` и `LLM_NUM_CTX=32768`.

Чтобы задать свои значения, создайте **`.env` в корне проекта**, рядом с
`docker-compose.yml`. Минимальный пример, сохраняющий стандартную модель:

```dotenv
OLLAMA_MODEL=qwen2.5-coder:7b
```

Для пробного запуска с меньшей моделью и короткими фрагментами кода:

```dotenv
OLLAMA_MODEL=qwen2.5-coder:1.5b
LLM_NUM_CTX=4096
LLM_MAX_OUTPUT_TOKENS=1024
```

Это альтернативные варианты одного файла. Меньшая модель может давать менее
подробные ответы; уменьшенный контекст ограничивает объём кода вместе с prompt
и ответом. Разрешённый размер в байтах не гарантирует, что текст поместится
в контекст модели: для такого профиля отправляйте небольшие примеры.

### Какие настройки откуда берутся

| Источник                | Использование                                                          |
| ----------------------- | ---------------------------------------------------------------------- |
| Корневой `.env`         | Compose подставляет значения в `${...}` из `docker-compose.yml`        |
| Переменные терминала    | Имеют приоритет над `.env` при подстановке Compose                     |
| `backend/.env`          | Используется backend при запуске без Docker; исключён из Docker-образа |
| `environment` в Compose | Задаёт окружение backend и загрузчика модели в контейнерах             |

Само добавление произвольной переменной в корневой `.env` не передаёт её
в контейнер. В текущем Compose `HOST=0.0.0.0` и
`OLLAMA_BASE_URL=http://ollama:11434` заданы явно; `PORT` не передаётся,
поэтому backend использует 5000. Запись `PORT=...` или `OLLAMA_BASE_URL=...`
в корневом `.env` это поведение не изменит. Для другого адреса Ollama потребуется
правка Compose; для обычного запуска она не нужна.
Подробности подстановки описаны в [документации Docker](https://docs.docker.com/compose/how-tos/environment-variables/variable-interpolation/).

Посмотрите итоговые настройки:

```sh
docker compose config --quiet
docker compose config
```

Первая команда при успехе ничего не выводит. Вторая показывает итоговую
конфигурацию после подстановки значений. Это проверка Compose, а не проверка
доступности модели или правильности всех числовых бюджетов backend.

### Доступные параметры backend

Все параметры из этой таблицы уже подключены в Compose и могут быть заданы
в корневом `.env`.

| Переменная                    |       По умолчанию | Назначение                                      |
| ----------------------------- | -----------------: | ----------------------------------------------- |
| `OLLAMA_MODEL`                | `qwen2.5-coder:7b` | Одна и та же модель для `ollama-init` и backend |
| `JSON_BODY_LIMIT_BYTES`       |             262144 | Максимальное JSON-тело, 256 КиБ                 |
| `MAX_CODE_BYTES`              |              32768 | Код в UTF-8, 32 КиБ                             |
| `MAX_CODE_LINES`              |               1000 | Максимальное число строк кода                   |
| `REVIEW_RATE_LIMIT_MAX`       |                  5 | Число попыток POST review за окно               |
| `REVIEW_RATE_LIMIT_WINDOW_MS` |              60000 | Окно ограничения частоты, мс                    |
| `MAX_CONCURRENT_REVIEWS`      |                  1 | Одновременные задачи review; очереди нет        |
| `REVIEW_TIMEOUT_MS`           |             300000 | Общий дедлайн анализа и генерации, мс           |
| `ANALYSIS_TIMEOUT_MS`         |               5000 | Дедлайн ESLint worker, мс                       |
| `ANALYSIS_MEMORY_MB`          |                128 | Лимит old-generation heap ESLint worker, МиБ    |
| `ANALYSIS_MAX_FINDINGS`       |                 20 | Число замечаний ESLint в отчёте                 |
| `ANALYSIS_MAX_OUTPUT_BYTES`   |               4096 | Размер отчёта ESLint в UTF-8                    |
| `LLM_NUM_CTX`                 |              32768 | Контекст модели, токены                         |
| `LLM_MAX_OUTPUT_TOKENS`       |               2048 | Максимум токенов генерации                      |
| `HTTP_REQUEST_TIMEOUT_MS`     |              30000 | Время получения HTTP-запроса backend, мс        |
| `HTTP_RESPONSE_TIMEOUT_MS`    |             330000 | Ожидание frontend и idle timeout backend, мс    |

Числа должны быть положительными целыми, не выше 2147483647.
Для `ANALYSIS_MEMORY_MB` минимум 32, для `ANALYSIS_MAX_OUTPUT_BYTES` — 64.
Backend проверяет следующие соотношения до запуска:

```text
ANALYSIS_TIMEOUT_MS <= REVIEW_TIMEOUT_MS
HTTP_RESPONSE_TIMEOUT_MS >= REVIEW_TIMEOUT_MS + HTTP_REQUEST_TIMEOUT_MS
MAX_CODE_BYTES <= JSON_BODY_LIMIT_BYTES
LLM_MAX_OUTPUT_TOKENS < LLM_NUM_CTX
```

В обоих Nginx дополнительно установлены фиксированные `client_max_body_size 256k`,
`client_body_timeout 30s`, `proxy_read_timeout 330s` и `proxy_send_timeout 330s`.
Если повышаете соответствующие размеры и таймауты backend, согласуйте их
с `apps/host/nginx.conf` и `apps/remote/nginx.conf`, затем пересоберите образы.
Для запуска без Docker также учитывайте таймауты в `webpack.config.js`.

## 5. Первый запуск

После подготовки рабочего каталога и, при необходимости, `.env`:

```sh
docker compose config --quiet
docker compose up -d --build
```

`--build` собирает backend и оба frontend; `-d` оставляет сервисы работать
в фоне. Несмотря на `-d`, сама команда может долго ждать зависимостей,
пока загружается модель. Ход подготовки можно смотреть во втором терминале:

```sh
docker compose logs -f ollama ollama-init
```

`Ctrl+C` в терминале с `logs -f` прекращает просмотр логов, сохраняя контейнеры.

Что происходит при запуске:

1. Docker получает базовые образы Node.js, Nginx и Ollama.
2. Backend устанавливает production-зависимости через `npm ci --omit=dev`.
   Frontend собираются через `npm ci` и `npm run build` в Node.js-контейнерах;
   готовые файлы копируются в финальные образы Nginx.
3. Стартует Ollama с volume `ollama_data`, смонтированным в `/root/.ollama`.
4. Healthcheck `ollama list` проверяет доступность сервера. Он запускается
   каждые 5 секунд, имеет timeout 3 секунды, 24 повтора и start period 10 секунд.
5. `ollama-init` выполняет `ollama show` для выбранной модели. Если модели нет,
   запускает `ollama pull`; при наличии использует уже скачанную.
6. Backend запускается после здорового состояния Ollama и успешного завершения
   `ollama-init`. Затем запускаются remote и host.

Healthcheck Ollama не проверяет генерацию. `ollama-init` скачивает модель,
но не прогревает её в памяти. Полную готовность подтверждает тестовое ревью.

Проверьте состояние:

```sh
docker compose ps -a
docker compose logs --tail=100 backend host remote
```

Ожидаемый результат:

| Сервис        | Нормальное состояние после подготовки                              |
| ------------- | ------------------------------------------------------------------ |
| `ollama`      | `Up` / `running`, health status `healthy`                          |
| `ollama-init` | `Exited (0)` — это успешное завершение одноразовой задачи          |
| `backend`     | `Up` / `running`; в логах `Backend running on http://0.0.0.0:5000` |
| `remote`      | `Up` / `running`, опубликован `127.0.0.1:3001`                     |
| `host`        | `Up` / `running`, опубликован `127.0.0.1:3000`                     |

У backend и frontend нет healthcheck, поэтому состояние `running` само по себе
не доказывает работоспособность API. Если загрузка модели завершается ошибкой,
зависимые сервисы не запускаются. После устранения причины повторите запуск;
если нужно гарантированно выполнить всю цепочку заново, используйте
`docker compose down`, затем `docker compose up -d --build`. Модели сохранятся.

## 6. Проверка приложения

### В браузере

Откройте основной интерфейс:

- [http://localhost:3000](http://localhost:3000) — host с загружаемым компонентом remote;
- [http://localhost:3001](http://localhost:3001) — remote отдельно, для диагностики.

В форме должны появиться ограничения API. Вставьте небольшой JavaScript-пример:

```javascript
const unused = 1;
console.log('hello');
```

Нажмите **Send for Review**. В результате ожидаются разделы `Static analysis:`
и `AI review:`; ESLint должен указать неиспользуемую переменную и пропущенную
точку с запятой. Текст AI-части может отличаться между моделями и запусками.
По умолчанию backend отводит до 300 секунд на задачу.

### Через API в PowerShell

Сначала проверьте API без обращения к модели:

```powershell
Invoke-RestMethod -Uri 'http://localhost:3000/api/review/limits'
Invoke-RestMethod -Uri 'http://localhost:3001/api/review/limits'
```

Оба адреса должны вернуть одинаковые ограничения. Затем выполните одно ревью:

```powershell
$reviewBody = @{ code = "const unused = 1; console.log('hello');" } | ConvertTo-Json -Compress
$reviewResponse = Invoke-RestMethod -Uri 'http://localhost:3000/api/review' -Method Post -ContentType 'application/json' -Body $reviewBody -TimeoutSec 340
$reviewResponse.review
```

### Через API в Bash

```sh
curl --fail-with-body http://localhost:3000/api/review/limits
curl --fail-with-body --max-time 340 \
  -H 'Content-Type: application/json' \
  -d '{"code":"const unused = 1; console.log(123);"}' \
  http://localhost:3000/api/review
```

Успешный POST возвращает JSON с полем `review` — строкой общего отчёта.
При увеличении серверных таймаутов увеличьте и timeout диагностического клиента.
В Windows PowerShell для curl-синтаксиса используйте `curl.exe`;
многострочный пример выше предназначен для Bash.

### Проверка контейнерной сети и модели

Эти команды не требуют публикации портов backend и Ollama:

```sh
docker compose exec ollama ollama list
docker compose exec backend node -e "fetch('http://ollama:11434/api/tags').then(r => { if (r.ok === false) throw new Error(String(r.status)); return r.json(); }).then(console.log).catch(e => { console.error(e.message); process.exitCode = 1; })"
```

Во втором ответе должна присутствовать выбранная модель. Команда проверяет сеть
от backend до Ollama, но ещё не проверяет генерацию. Модель, установленная
в Ollama на компьютере вне Docker, автоматически в этот volume не переносится.

## 7. Повторный запуск, изменения и остановка

### Обычная работа

Показать состояние и последние логи:

```sh
docker compose ps -a
docker compose logs --tail=100 backend ollama ollama-init
```

Остановить контейнеры без удаления:

```sh
docker compose stop
```

Запустить существующую конфигурацию снова:

```sh
docker compose up -d
```

Удалить контейнеры и сеть, сохранив скачанные модели:

```sh
docker compose down
```

При обычной остановке volume остаётся. Его фактическое имя обычно имеет вид
`ai-code-reviewer_ollama_data`: префикс зависит от имени Compose-проекта.
Используйте одну и ту же директорию проекта и одно имя проекта, иначе Compose
может создать другой volume, и модель будет скачиваться заново.

Для полного удаления данных моделей, только если они больше не нужны:

```sh
docker compose down -v
```

Следующий запуск после `down -v` снова потребует скачать модель.

### Изменение модели или `.env`

Отредактируйте корневой `.env`, затем выполните:

```sh
docker compose config --quiet
docker compose down
docker compose up -d
```

Так загрузчик снова проверит выбранную модель, backend получит новое окружение,
а Nginx запустится с актуальными адресами контейнеров. Старые модели сохраняются
в volume. Пересборка образов ради изменения только `.env` не требуется.

`docker compose restart` не применяет изменения окружения или Compose:
это отдельно оговорено в [справочнике Docker](https://docs.docker.com/reference/cli/docker/compose/restart/).

### Изменение исходников, зависимостей или Nginx

В Compose нет bind mounts исходников: изменения файлов на компьютере не попадут
в работающие контейнеры автоматически. После изменений:

```sh
docker compose down
docker compose up -d --build
```

Остановка всего стека перед пересозданием backend также исключает ситуацию,
когда оставшийся Nginx использует ранее разрешённый IP backend.

Чтобы отдельно обновить внешние образы Ollama и базовые образы сборки:

```sh
docker compose pull ollama ollama-init
docker compose build --pull
docker compose down
docker compose up -d
```

Обычный `up --build` не гарантирует скачивание более свежего базового образа.
В текущем Compose нет автоматического перезапуска постоянных сервисов:
для восстановления после сбоя или перезагрузки проверьте Docker и выполните
`docker compose up -d`.

## 8. Использование NVIDIA GPU

NVIDIA GPU уже включён в основном `docker-compose.yml`. Ollama и `ollama-init`
используют одну версию образа — `ollama/ollama:0.40.5`. Сервер ограничен одним
параллельным запросом и одной загруженной моделью.

На Windows для доступа Linux-контейнеров к NVIDIA GPU нужны WSL 2 backend,
совместимая видеокарта и актуальный драйвер с поддержкой WSL. Подробности —
в [инструкции Docker Desktop](https://docs.docker.com/desktop/features/gpu/).
Для обычного Docker Engine на Linux подготовьте драйвер и NVIDIA Container
Toolkit по [инструкции Ollama](https://docs.ollama.com/docker).

Доступ к GPU запрошен внутри сервиса `ollama`:

```yaml
deploy:
  resources:
    reservations:
      devices:
        - driver: nvidia
          count: all
          capabilities: [gpu]
```

Настройка нужна серверу Ollama; для `ollama-init` она не требуется.
Такой способ описан в [документации GPU для Compose](https://docs.docker.com/compose/how-tos/gpu-support/).
Чтобы применить настройки к существующему контейнеру Ollama:

```sh
docker compose config --quiet
docker compose up -d --no-deps ollama
docker compose logs --tail=100 ollama
```

Запустите ревью и, пока модель загружена, проверьте:

```sh
docker compose exec ollama ollama ps
```

Поле `PROCESSOR` показывает размещение модели на CPU/GPU.
Если активной модели нет, вывод может быть пустым. Доступность GPU не гарантирует,
что выбранная модель вместе с контекстом полностью поместится в VRAM.

## 9. Типичные проблемы

| Симптом                                                                       | Что проверить и сделать                                                                                                                                                                                     |
| ----------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `docker` не найден                                                            | Установку Docker и PATH; после установки откройте новый терминал                                                                                                                                            |
| `Cannot connect to the Docker daemon`, ошибка named pipe, `permission denied` | Работает ли Docker Desktop/Engine, какой контекст выбран (`docker context ls`), есть ли у пользователя или среды выполнения доступ к движку; в Windows используйте Linux-контекст, созданный Docker Desktop |
| `port is already allocated` для 3000/3001                                     | Остановите ранее запущенные webpack dev server или другой свой процесс, занявший порт; это стандартные порты обоих frontend                                                                                 |
| Конфликт имени контейнера `ollama`                                            | В Compose задано фиксированное `container_name: ollama`; проверьте `docker ps -a --filter name=ollama`. Для нескольких независимых стеков потребуется изменить или убрать это имя; смены `-p` недостаточно  |
| Долго нет интерфейса, `ollama-init` работает                                  | Посмотрите `docker compose logs -f ollama-init`: первый запуск скачивает модель до старта backend                                                                                                           |
| `ollama-init` завершился с ненулевым кодом                                    | Проверьте `OLLAMA_MODEL`, доступ к реестру из контейнера, прокси и свободное место; после исправления выполните `down`, затем `up -d --build` без `-v`                                                      |
| Ollama `unhealthy`                                                            | `docker compose logs --tail=100 ollama`, ресурсы Docker, `docker compose exec ollama ollama list`; backend ждёт успешного healthcheck                                                                       |
| Backend завершается сразу                                                     | В логах backend проверьте сообщение валидации переменных и связанные бюджеты из раздела 4                                                                                                                   |
| Форма пишет, что не удалось получить ограничения API                          | Проверьте `/api/review/limits`, логи `backend`, `host`, `remote`; интерфейс не отправляет ревью без доступных лимитов                                                                                       |
| Host пустой, remote отдельно работает                                         | В инструментах разработчика браузера проверьте `/remote/remoteEntry.js` и чанки; затем логи host/remote и наличие сервиса remote                                                                            |
| HTTP 502 с `{ "error": "Ollama request failed..." }`                          | Backend доступен, но запрос модели не удался; проверьте список моделей, логи Ollama и нехватку RAM/VRAM                                                                                                     |
| HTTP 502 и HTML от Nginx                                                      | Проверьте доступность backend и логи Nginx; после отдельного пересоздания backend перезапустите `host` и `remote` для повторного разрешения его адреса                                                      |
| HTTP 504 с JSON `Review timed out`                                            | Истёк общий дедлайн 300 секунд; попробуйте короткий код, меньшую модель/контекст или GPU. Для увеличения таймаута изменяйте согласованно backend и оба Nginx                                                |
| Контейнер завершился с кодом 137                                              | Возможна нехватка памяти; проверьте `docker stats`, лимиты Docker/WSL и `docker inspect` для нужного контейнера, включая `State.OOMKilled`                                                                  |
| HTTP 429                                                                      | Общая квота — 5 попыток за 60 секунд и 1 активная задача; дождитесь завершения и учитывайте `Retry-After`. Неудачные попытки также учитываются                                                              |
| HTTP 413                                                                      | Слишком большой JSON, больше 32 КиБ кода или больше 1000 строк; отправьте меньший фрагмент                                                                                                                  |
| HTTP 403 после смены порта или адреса                                         | Backend разрешает Origin только `http://localhost:3000`, `http://127.0.0.1:3000`, `http://localhost:3001`, `http://127.0.0.1:3001`; одного изменения `ports` недостаточно                                   |
| HTTP 400, 415 или 422                                                         | Проверьте JSON с непустым строковым `code`, `Content-Type: application/json`, отсутствие сжатия; 422 означает превышение времени/ресурсов статического анализа                                              |
| Очень большой build context или ошибки пакетов frontend                       | Проверьте наличие и правила frontend `.dockerignore` согласно разделу 3 и пересоберите образы                                                                                                               |
| Ошибки скачивания npm-пакетов или образов                                     | Проверьте сеть/прокси Docker Desktop и доступ к npm/Docker Hub; локальный `npm install` не исправит отсутствие сети у сборки контейнера                                                                     |
| После исправления файлов ничего не изменилось                                 | Пересоберите образы: `down`, затем `up -d --build`; исходники не смонтированы в контейнеры                                                                                                                  |

Backend не имеет маршрута `/health`, а его корневой `/` возвращает 404.
Для проверки API используйте `/api/review/limits` через frontend.
`http://localhost:5000` и `http://localhost:11434` не являются адресами проверки
этого Docker-стека: соответствующие порты не опубликованы.

## 10. Особенности текущей Docker-конфигурации

Это результаты анализа репозитория, которые стоит учитывать при поддержке:

- Backend использует `node:24-alpine` и `npm ci --omit=dev`; оба frontend
  собираются в `node:24-alpine` через `npm ci`. CI и локальные проверки также
  рассчитаны на Node.js 24.
- `backend`, `apps/host` и `apps/remote` — независимые npm-пакеты, каждый со своими
  `package.json` и `package-lock.json`. Зависимости устанавливаются отдельно для
  каждого приложения через `npm ci`; backend исключает devDependencies, frontend
  сохраняют их на этапе сборки. Lock-файлы должны соответствовать манифестам.
- Корневой npm-пакет и его lock-файл относятся к линтингу и общему запуску проверок.
  Они не входят в build context приложений и не нужны внутри Docker-образов.
- Ollama и загрузчик закреплены на версии `0.40.5`. Для точного воспроизведения
  можно закрепить digest; теги `nginx:alpine` и `node:24-alpine` по-прежнему
  допускают обновление содержимого.
- В CI проверяется `docker compose config --quiet` и запускается `npm run check`:
  линтинг, проверка типов, тесты backend, dev proxy и формы remote, затем сборки
  обоих frontend. Полной сборки Docker-образов, браузерной проверки Module Federation
  и генерации ответа настоящей моделью в CI нет.
- `ollama-init: Exited (0)` ожидаем; запуск всего стека с
  `--abort-on-container-exit` не подходит, поскольку одноразовый сервис
  должен завершаться.
- Backend и оба интерфейса не имеют healthcheck; зависимости frontend ждут
  запуска процесса backend, а не успешного HTTP-запроса. Проверка из раздела 6
  нужна после первого запуска и обновлений.
- Backend-образ исключает каталог `test` и devDependencies. Для тестов проекта
  используйте предусмотренный в README локальный/CI-сценарий, а не
  `docker compose exec backend npm test` как подтверждение всех тестов.
- Интерфейсы опубликованы на `127.0.0.1`; API и Ollama доступны через внутреннюю
  сеть Compose. Аутентификации в приложении нет: текущий сценарий рассчитан
  на одного пользователя на доверенной локальной машине. Для публикации
  на сервере потребуются отдельная настройка доступа, HTTPS и разрешённых Origin.
